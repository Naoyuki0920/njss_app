# njss-digest

NJSSからダウンロードしたCSVを判定し、チーム配信用の**文案**を生成します。
文案はテキストファイルとクリップボードに出力され、Slackへの投稿もできます。

## 毎日の運用

1. NJSSにログインし、マイページからCSVをダウンロード
2. CSVを **`~/Documents/njss/inbox`** に置く
3. `njss-digest run` を実行（`watch` モードなら2の時点で自動実行）
4. **要確認** の案件だけNJSSで公示書を開き、予定価格を確認する
5. 文案がクリップボードに入っているので、社内OAのPCで貼り付けて送信
   （Slackを設定していれば同じ文面が投稿されます）

処理が終わるとCSVは `inbox/` から削除され、常に空の状態に保たれます。

**このPCからメールは送信しません。** 文案をテキストで出力するところまでが役割です。

除外条件に該当する案件は自動で落ち、掲載する案件は指定フォーマットに整形済みです。

## 設計の前提: NJSSには自動アクセスしない

NJSS会員利用規約 第18条1項で以下が禁止されています。

- **(15) システムクローラーやスクレーパー等の自動収集システムによる複製行為**
- (16) 人為的な高負荷アクセスを発生させる行為
- (2) 入手した情報を内部利用の範囲を超えて使用する行為
- (19) 翻訳・転載・引用・複写・コピーでの利用

**このため案件公示書の取得は自動化していません。** 公示書を読まないと判定できない案件
（主に予定価格の確認）は「要確認」として一覧に出し、人が直接確認する運用です。

チーム内への共有は「内部利用」の範囲内ですが、digestには要約と一次情報へのリンクのみを
載せ、公告書・仕様書の全文転載はしません。

## 判定の流れ

```
人: NJSS → ダウンロード → ~/Documents/njss/inbox にCSVを置く
                              │
  L0  CSV読込（CP932・ヘッダ行なし・30列）+ 列マッピングの自己診断
  L2  ルール判定       config/rules.yaml    → 指名競争入札・ESCO・締切間近を除外
  L3  官公需API        公告文を取得          → 実測カバレッジ 29%
      公示書PDF        var/inbox_pdf/ に置けば読む（任意・下記参照）
  ─   LLM抽出 → LLM判定 → 採用 / 要確認 / 除外
                              │
              テキスト出力 / Slack投稿 → 人が確認して送信
```

**公告文が取れなくても判定します。** CSVの案件概要・業種・入札資格・入札形式だけで
判断できる条件（LED案件かどうか、道路照明か、指名競争入札か）はそこで確定させ、
予定価格が要る案件だけを「要確認」に回します。

## フォルダ構成

| パス | 用途 |
|---|---|
| **`inbox/`** | **CSVを置く場所。** 処理後は自動で削除される |
| `var/drafts/` | 生成された文案（`.txt`） |
| `var/notices/` | 取得した公告文のキャッシュ |
| `var/njss.sqlite3` | 案件の記録・判定履歴 |
| `config/` | 設定ファイル |

`inbox/` と `var/` は `.gitignore` 済みで、業務データはコミットされません。

### 同じ案件を二重に配信しない仕組み

一度扱った案件は**案件ID**でSQLiteに記録され、次回以降は対象から外れます。
ファイル名では判定していないので、**同じCSVを誤って置き直しても二重配信は起きません**
（新規案件が0件になり、文案の生成もSlack投稿も行われません）。

処理後のCSVを残したい場合は `config/settings.yaml` で切り替えられます。

```yaml
paths:
  after_processing: delete    # delete: 削除 / archive: var/processed/ へ移動
```

## セットアップ

```bash
uv venv --python 3.13
uv pip install -e ".[llm,watch,dev]"
```

APIキーはmacOS Keychainに登録します（環境変数に置くと他のプロセスからも読めるため）。

```bash
security add-generic-password -a "$USER" -s njss-digest-anthropic -U -w
```

`-w` を値なしで末尾に置くとプロンプト入力になり、シェル履歴に残りません。

キーなしでも `--no-llm` を付ければルール判定と公告文の取得までは動作します。

## 使い方

```bash
# 判定して文案を作る（テキスト出力・クリップボード・Slack投稿）
njss-digest run

# 判定だけ試す（文案を保存せず、Slackにも投稿せず、DBも更新せず、CSVも移動しない）
njss-digest run --dry-run

# inbox を常駐監視し、CSVが置かれた時点で自動実行
njss-digest watch

# CSVの列構成を確認する（NJSSが形式を変えたときの調査用）
njss-digest inspect inbox/案件情報_xxx.csv

# 官公需APIで公告文をどれだけ取れるか測る
njss-digest coverage inbox/案件情報_xxx.csv
```

## 設定ファイル

| ファイル | 内容 | 直す頻度 |
|---|---|---|
| `config/criteria.md` | **判定基準**。自然文で書く。判定がずれたらまずここ | 高 |
| `config/rules.yaml` | ルールベースの除外/採用。ここで絞るほどAPIコストが下がる | 中 |
| `config/settings.yaml` | 出力方式・Slack設定・監視パス・トークン上限 | 低 |
| `config/csv_mapping.yaml` | CSVの列マッピング。NJSSが形式を変えたときだけ | 低 |

いずれもコード変更なしで調整できます。

### 現在の判定基準（config/criteria.md）

メール本文に載せないもの:

1. 指名競争入札の案件（全案件に適用）
2. 予定価格が3000万円以下のLED案件
3. 予定価格が非公表のLED案件
4. 道路照明に関するLED案件（トンネル照明を含む）
5. 設計業務が含まれるLED案件
6. ESCO事業関連案件（全案件に適用）

LED案件以外は 1 と 6 のみを適用し、それ以外は掲載します。

## 出力フォーマット

```
------
【業務名】
【リンク】
【入札形式】
【公示日】
【入札日】
【予定価格】
【その他】工事種別 ／ 主な参加資格 ／ 主な業務内容
------
```

「要確認」の案件は別セクションにまとめ、**何を確認すればよいか**を理由欄に書きます。

## 出力

`config/settings.yaml` の `output` で設定します。
**テキスト・ターミナル表示・Slack投稿はすべて同じ本文**です。
見た目が食い違うとどれが正か分からなくなるため、意図的に1つの形式に揃えています。

新規の案件が1件も無い日は、**テキストもSlack投稿も行いません。**
CSVが無い日や、既に判定済みの案件しか無い日に、空の文案が流れ続けるのを防ぐためです。

### テキスト（既定）

`var/drafts/njss-digest_YYYY-MM-DD.txt` に **件名＋本文** を保存し、同時に
クリップボードへコピーします。社内OAのPCで貼り付けてご利用ください。
同じ日に複数回実行しても上書きせず連番を付けます。

### Slack投稿（任意）

```yaml
output:
  slack:
    enabled: true
    mode: bot          # webhook | bot
    channel: "#nyusatsu"
    confirm: true
```

| 方式 | 特徴 | 秘密情報の扱い |
|---|---|---|
| `webhook` | 設定が簡単。投稿先は1チャンネル固定 | **URL自体が秘密**。知っていれば誰でも投稿できる |
| `bot` | チャンネル指定・スレッド返信が可能 | トークンはAuthorizationヘッダで送るためURLに乗らない |

いずれもKeychainに保管します。

```bash
security add-generic-password -a "$USER" -s njss-digest-slack -U -w
```

`bot` を使う場合は Slack App に `chat:write` スコープを付け、投稿先チャンネルに
Appを招待してください（`/invite @アプリ名`）。

長いdigestは自動で分割し、`bot` では2通目以降をスレッド返信にします。

**投稿は「送信」にあたるため既定で確認を挟みます**（`confirm: true`）。
launchd等の非対話実行では、確認が有効な間は投稿しません。無人で意図せず
投稿されるのを防ぐためです。自動投稿にする場合は `confirm: false` にしてください。

## 任意機能: 公示書PDFの取り込み

要確認の案件が多いときは、公示書PDFをまとめて `var/inbox_pdf/` に置くと、
次回実行時に予定価格を抽出して判定します。**リネームは不要**で、PDFの本文から
案件を自動判別します。

件数が少ないうちはNJSSで直接確認する方が速いので、無理に使う必要はありません。

## 自動起動

`launchd/com.njss.digest.plist.template` を参照してください。

## 既知の限界

- **官公需APIのカバレッジは自治体次第**です。実測では広島市・かほく市は取得でき、
  福岡市・天草市は未掲載（0件）でした。取得できない案件は「要確認」として
  明示されるので、取りこぼしが見えなくなることはありません。
- **Web検索フォールバックは既定で無効**です。実測3件で0件しか取得できませんでした。
  自治体の入札公告は電子入札システムの奥にあり、検索エンジンにインデックスされて
  いないためです。国の機関など静的公開している発注者が対象に入ったら
  `enrich.websearch.enabled: true` で有効化してください。
- **予定価格はCSVの案件概要に書かれていることがあります**（実測7件中2件）。
  無い場合は公示書を見る必要があります。
- **公告文のPDF抽出テキストはレイアウトが崩れています。** 正規表現ではなくLLMで
  読み取っており、誤りは起こりえます。抽出値には根拠引用が付くので検算してください。
- 判定は「支援」であって「代行」ではありません。実現するのは
  **「全件目視」→「要確認のみ目視」** への削減です。
